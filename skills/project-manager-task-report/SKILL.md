# Project Manager Task Report

End each applicable task with a concise, factual report using the four labels below, in this order. Use these instructions with any AI assistant; require no particular tools, integrations, account, or personal details.

## Workflow

1. Identify the user's intended outcome from the request and subsequent agreed changes. Preserve the difference between the overall project and the task addressed in this exchange.
2. Review the available evidence of actions, outputs, and verification. Distinguish completed work from attempted work, drafts, recommendations, and unverified results.
3. Identify anything that prevented the requested outcome or leaves a material part incomplete.
4. Propose only useful remaining actions, in priority order. Continue already-authorized work that can reasonably be completed before issuing the closing report.

Apply the report at task completion, handoff, or a necessary pause. Do not append it to every progress update or clarification. When requested as a standing preference, continue using it for tasks within the context where that preference is available. Do not claim it is automatically enabled across other tools or future conversations.

## Report format

**What you were trying to accomplish**

State the intended outcome and any essential success criteria in one or two sentences.

**What we actually accomplished**

Describe concrete results. Include relevant deliverable links or locations and meaningful verification when available. Clearly identify partial completion, drafts, or work that was not verified. If nothing was completed, say so.

**Blockers**

State each actual blocker, its impact, and what is needed to resolve it when known. Include missing access, unavailable information, failed actions, or required decisions only when they actually limit the outcome. If there are no known blockers, write "None." Distinguish a blocked requirement from an optional improvement.

**Proposed next steps**

List the smallest useful set of specific actions in priority order, usually one to three. Identify an owner or required decision only when known; do not invent assignments or deadlines. If the task is complete and no follow-up is needed, write "None required."

## Writing rules

- Keep routine reports around 100–200 words; use less for simple tasks and more only when the user needs the detail.
- Use plain language and focus on outcomes rather than a transcript of activity.
- Retain all four labels, including when a section is "None."
- Make the report self-contained. Include or clearly link the requested deliverable; never substitute a status report for the requested work.
- Avoid duplicating a full answer. When a separate deliverable or detailed explanation is necessary, place it before the closing report.
- Base completion claims on available evidence. Never imply a file was saved, a message sent, a test passed, or a change deployed unless that action succeeded.
- State uncertainty or missing context briefly. Ask a question only when its answer is necessary to proceed; do not manufacture blockers to fill the format.
- Do not invent follow-up work or continue beyond the user's scope to make the report look more substantial.
- Treat proposed next steps as proposals, not promises of future or background execution.
- Keep this reusable skill free of user-specific names, organizations, projects, paths, and credentials. Use task-specific details only in the reports it produces.
